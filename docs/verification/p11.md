## Scenario evidence

- The Mac creates a short-lived challenge authorizing Personal only. A separate sandboxed companion pairs once and sees Personal but not Work.
- A forged Work request with a valid Personal device credential is rejected at the API boundary.
- Retrying one Personal submission with the same idempotency key creates one OpenRouter task. Reusing the key with a different payload fails.
- Cursor reads return ordered companion events and return no duplicates after reconnect from the latest cursor.
- The companion prepares a Plan-the-Day Codex prompt with zero provider calls. Copy occurs only after the user presses the companion copy button.
- A companion voice turn produces a task in Personal and none in Work. Voice playback/interruption routes through the P10 session boundary.
- An unavailable host rejects a new request without recording or replaying it after availability returns.
- Revoking the open companion from the Mac makes its next authenticated request fail immediately.
- Server metadata contains only the token digest, never the raw device credential.

## Honest boundaries and pending acceptance

- No actual phone, LAN address, certificate trust chain, firewall rule, sleep/wake, Wi-Fi transition, or long reconnect was exercised.
- There is no internet relay, push notification service, background execution while the Mac sleeps, or stale run-on-wake queue.
- Remote voice uses text/provider fixtures; P10's physical audio and language acceptance remains applicable.
